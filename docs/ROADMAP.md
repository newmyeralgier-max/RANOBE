# ROADMAP — план следующих фич

Этот документ — рабочий список того, что мы пилим после первой стабильной версии. Он живёт в репо специально, чтобы агент мог между сессиями восстанавливать контекст и не терять выбранные приоритеты. Если планы меняются — правим этот файл, не помним «в голове».

Стиль: фазами, сверху вниз. Каждая следующая фаза опирается на предыдущую. Внутри фазы пункты как правило независимы — можно тасовать.

---

## Текущее состояние (на старте плана)

- Архитектура: `execution/novel_dl/` — пакет, точки входа `__main__.py` (CLI) и `gui.py` (Tk).
- Адаптеры в `adapters/` (FreeWebNovel, ranobes), регистрация через `registry.py`.
- Скачивание: `downloader.py` последовательное, с задержкой 1.5±30%.
- Перевод: `translator.py`, Cohere `/v2/chat`, чанки 6000 символов, 3 ретрая, temperature 0.1→0.3.
- EPUB: `epub.py` — stdlib `zipfile`, минимальный валидный EPUB3.
- Настройки: `settings.py` — JSON `~/.novel_dl/config.json`, атомарная запись.
- GUI: `gui.py` (1049 строк) — одно большое окно, очередь сообщений, кнопки Скачать / Перевести / Собрать EPUB.
- Тесты: `tests/test_universal.py`, 36 шт., моки сети.
- Лончеры: `launchers/novel_dl.bat` (Windows), `novel_dl.sh` (Linux/macOS).

## Фаза 1 — Фундамент (чтобы остальные фазы было не больно делать)

Эти изменения — рефакторинг внутрянки. Внешне почти ничего не меняется, но без них следующие пункты будут хрупкими.

### 1.1. Settings: списки вместо одиночных значений
**Зачем:** для пункта 2 (последние 5 URL/ключей).
**Файл:** `execution/novel_dl/settings.py`.
**Что меняем:**
- В `DEFAULTS` добавляем `recent_urls: list[str] = []`, `recent_api_keys: list[str] = []` (ключи только если `save_api_key=True`).
- Хелперы `push_recent(key, value, max=5)` и `get_recent(key)`.
- Миграция: при загрузке старого конфига одиночные `url`/`api_key` подтягиваются в начало списка.
**Риск:** низкий. Полностью обратно-совместимо.

### 1.2. Settings: автосохранение при изменении (пункт 19)
**Зачем:** сейчас настройки пишутся только по кнопке «Сохранить». Если приложение упало — потеря.
**Что:** в GUI на каждое поле повесить `trace_add("write", _on_setting_changed)`. Дебаунс 500мс, чтобы не писать 100 раз пока юзер печатает URL.
**Файлы:** `gui.py`. `settings.py` уже атомарен — лишняя запись безопасна.
**Тонкость:** для `api_key` всё ещё уважать `save_api_key` чекбокс.

### 1.3. Логирование в файл (пункт 20)
**Зачем:** если что-то упало вне поля видимости — есть `~/.novel_dl/runs/2025-04-23-1530.log` для разбора.
**Что:**
- В `gui.py` создать `RunLogger` — пишет тот же поток, что идёт в Text-виджет, плюс stderr-сообщения.
- Имя файла: `<config_dir>/runs/YYYY-MM-DD-HHMMSS.log`. Старые файлы (>30 шт.) удаляем при старте.
- Кнопка «Открыть лог» рядом с Text — открывает файл текущего запуска в системном редакторе (`os.startfile` / `xdg-open` / `open`).
- В CLI (`cli.py`) — то же самое, только без кнопки.
**Размер:** ~80 строк нового кода, изоляция в новом модуле `runlog.py`.

### 1.4. Авто-бэкап скачанных глав (пункт 17)
**Зачем:** «случайно нажал не туда» — главы исчезли, перекачивать долго.
**Что:** при старте каждой большой операции (Скачать / Перевести / EPUB) — создавать `<output_dir>/backups/<YYYY-MM-DD-HHMM>/` и **жёстко-линковать** туда уже существующие `chapter_*.txt` (мгновенно, не занимает места). На Windows fallback на `shutil.copy2`. Чистка: оставляем последние 5 бэкапов.
**Файл:** новый `backup.py`, ~50 строк. Вызов из `gui.py` перед запуском операции.
**Риск:** низкий.

### 2.2. Прогресс по символам (пункт 4)
**Зачем:** на длинной главе бар сейчас стоит на месте, кажется что зависло.
**Что:**

### 2.3. Колонка статуса для каждой главы (пункт 5)

**Сложность:** средняя — в Tk Treeview капризный, но шаблонов много.

### 2.4. Тёмная тема (пункт 6)
**Что:** галочка «Тёмная тема» в правом верхнем углу. Под капотом — `ttk.Style` с двумя темами, переключатель + сохранение в settings.
**Реализация:** не тащить лишних зависимостей, хватит `sun-valley.tcl` (~10 КБ, MIT) — кладём как `assets/sun-valley.tcl`, грузим через `root.tk.call("source", path)`. Альтернатива: ручная палитра, но получится бледно.
**Размер:** ~30 строк + один tcl-файл.

### 2.5. Пауза/возобновление (пункт 3)
**Зачем:** Cohere подвисает — лучше нажать «Пауза» на 5 минут, чем убивать всю прогон.
**Что:**
- В `translator.translate_dir`: добавить `pause_event: threading.Event` (set = идти, clear = пауза). Перед каждым HTTP-запросом ждём `pause_event.wait()`.
- В GUI кнопка «⏸ Пауза» рядом со «Стоп». Клик — clear, повторный — set.
- Аналогично в `downloader.py`.
**Размер:** ~15 строк в каждом из двух файлов.

### 2.6. Авто-проверка обновлений (пункт 16)
**Зачем:** юзер не помнит делать `git pull`, сидит на старой версии часами.
**Что:**
- При старте GUI в фоновом потоке: `git -C <repo> fetch origin <branch>` (3 сек таймаут, тихо игнорируем ошибки).
- `git rev-list HEAD..origin/<branch> --count` → если >0 — в правом верхнем углу баннер «🆕 Доступно N обновлений → Применить».
- Клик «Применить» = `git pull --ff-only`, потом «Перезапустить приложение?» messagebox.
**Файл:** новый `updater.py`. Важно: не делать ничего если репо в detached HEAD или с локальными изменениями — только показать баннер «есть обновления, обнови вручную».
**Риск:** средний — `git pull` может конфликтовать. Стратегия — ТОЛЬКО `--ff-only`, при ошибке просим юзера вручную.

## Фаза 3 — Качество перевода (приоритет, пункт 8 «обязательно»)

### 3.1. Глоссарий (пункт 8)
**Зачем:** без него ИИ переводит «John» как «Иван» в одной главе и «Джон» в другой. Ломает консистентность.
**Что:**
- Файл `<output_dir>/glossary.json`: `{"John Smith": "Джон Смит", "Sword Saint": "Святой Меча", ...}`.
- Новая вкладка «Глоссарий» в GUI: таблица из 2 колонок, Add/Edit/Delete, кнопки «Импорт/Экспорт» (.json и .csv).
- Авто-извлечение из переводов: при каждом завершённом переводе запускаем `extract_proper_nouns(en, ru)` — ищем повторяющиеся 1-3-словные кандидаты, предлагаем добавить в глоссарий через popup «Найдены новые имена: [✓] John Smith → Джон Смит, [ ] another».
- Подстановка в промпт: блок «GLOSSARY (use these spellings strictly):\n- John Smith = Джон Смит\n...», вставляется в system prompt перед каждой главой.
- Если глоссарий >100 строк, подаётся только релевантная часть (только те имена что встретились в текущем чанке).
**Размер:** ~250 строк нового кода (`glossary.py` + UI). Самая большая фича в этой фазе.
**Тесты:** обязательно — добавить unit-тесты для извлечения имён, инжекции в промпт, сохранения/загрузки.

### 3.2. Память контекста (пункт 9)
**Зачем:** «вы→ты», смены рода персонажей, имена прыгают на разных вариантах.
**Что:**
- При переводе главы N — в system prompt добавляем «Previous context (last 2 paragraphs of chapter N-1, already translated): ...». Кладём russian версию (она уже определила «вы» или «ты»).
- Хранение: для каждой `chapter_NNNN_*.ru.txt` извлекаем последние 2 абзаца, кэшируем в памяти на сессию.
- Лимит длины: ~800 символов. Если первая глава — пусто.
**Файл:** `translator.py`, +20 строк.
**Связь с 3.1:** оба влезают в один system prompt — порядок: правила → глоссарий → контекст → текст.

### 4.1. Альтернативные провайдеры — каркас, UI неактивен (пункт 11, на будущее)
**Зачем:** чтоб когда понадобится переключить — не переписывать пол-проекта.
**Что:**

- В GUI — `ttk.Combobox` «Провайдер: [Cohere v]», варианты `OpenAI`, `Anthropic`, `DeepSeek` — **disabled / serой**, при ховере tooltip «скоро».
**Размер:** ~80 строк рефакторинга, тесты должны продолжить работать.

### 4.2. Двуязычный EPUB (пункт 12, отдельная заметная галочка)
**Зачем:** учить язык на интересной книжке.
**Что:**
- Чекбокс «Двуязычный EPUB (en+ru параллельно)» в панели EPUB, **рамкой выделен**, default off.
- Если включён: каждая глава в EPUB = пары абзацев `<p class="en">...</p>` (серый, мельче) + `<p class="ru">...</p>`.
- Сопоставление абзацев: по индексу. Если разное число абзацев между en и ru — добавляем пустые с пометкой «(пропуск)».
- В CSS добавить `.en{color:#888;font-size:0.85em;font-style:italic}`.
**Файл:** `epub.py`, `gui.py`. ~100 строк.
**Риск:** средний — абзацы могут не совпадать по числу.

### 4.3. Ретрай при потере интернета (пункт 18)
**Зачем:** VPN моргнул — приложение убивается, прогресс теряется.
**Что:** в обоих местах (downloader, translator) — обернуть HTTP в общий `with_network_retry(fn, max_wait=600)`. Если падает с `URLError`/`ConnectionError`/`TimeoutError`, ждать 30→60→120→240→480 сек, проверяя `is_online()` (HEAD на `https://1.1.1.1`). При 5 неудачах подряд — честная ошибка «нет интернета 8+ минут, останавливаюсь».
**Файл:** новый `netretry.py`, ~60 строк. Вызовы из `downloader.py`, `translator.py`.

## Фаза 5 — Скорость

⚠️ **Риск:** оба пункта могут спровоцировать антибот / rate-limit. Делаем с консервативными дефолтами и явной кнопкой «Турбо-режим».

### 5.1. Параллельная скачка (пункт 13)
**Что:** `ThreadPoolExecutor(max_workers=3)`. **НЕ 5** — ranobes ловит Cloudflare уже сейчас на 1.5 сек/гл. С 3 потоками = 0.5 сек/гл — на грани.
- Чекбокс «Параллельная скачка (3 потока)» в GUI, default off.
- Глобальный rate-limiter: суммарно не более 1 запроса каждые 0.4 сек, чтобы суммарная нагрузка на сайт не превышала ~2.5 RPS.
- Если хоть один поток ловит Cloudflare — все остальные приостанавливаются на 60 сек.
**Файл:** `downloader.py`, ~40 строк.
**Тесты:** мок 50 «глав», проверка что концурренси работает + rate-limit держится.

### 5.2. Параллельный перевод (пункт 14)
**Что:** аналогично, `ThreadPoolExecutor(max_workers=2)` (Cohere пускает по умолчанию ~10 RPS, но 2 потока = безопаснее, плюс уменьшит шанс получить 429).
- Чекбокс «Параллельный перевод (2 потока)», default off.
- При 429/503 — все потоки на паузу 60 сек.
- Глоссарий и контекст-память (3.1, 3.2) — потокобезопасные, читают из общего dict.
**Файл:** `translator.py`, ~30 строк.

**Файл:** новый `importer.py`, ~200 строк. Зависимости — только stdlib (`xml.etree`, `zipfile`).

## Фаза 7 — Telegram-бот (пункт 28, «было бы охуенно»)

**Цель:** пишешь боту URL → через час получаешь EPUB в личку.

**Архитектура:**
- Отдельная папка `tg_bot/` рядом с `execution/`.
- `tg_bot/bot.py` — long-polling через `aiogram` (или `python-telegram-bot`, что свежее на момент реализации).
- `tg_bot/queue.py` — очередь задач на диске (`~/.novel_dl/tg_queue.json`), чтоб переживать рестарт.
- `tg_bot/worker.py` — синхронная обёртка вокруг `novel_dl.cli`, отправляет статус-апдейты в чат.
- Хостинг: пользователь у себя на ПК. На отдельной машине = усложнение, не нужно сейчас.

**Команды:**
- `/start` — приветствие, статус доступа (только белый список chat_id из `~/.novel_dl/tg_allowed.json`).
- `/dl <url>` — поставить в очередь (диапазон по умолчанию `all`, перевод вкл, EPUB ru).
- `/dl <url> 1-100 en` — кастом параметры.
- `/queue` — список своих задач.
- `/cancel <id>` — отмена.
- `/status` — что прямо сейчас делается.

**Авторизация:**
- Первый `chat_id` который пишет `/start` после первого запуска — становится «админом».
- Админ через `/allow <chat_id>` пускает других.

**Конфиг:** `~/.novel_dl/tg_bot.json` с `bot_token`, `cohere_api_key`, `allowed_chat_ids: list`. Токен бот-юзер получает у `@BotFather`.

**Запуск:** новый `launchers/tg_bot.bat` и `tg_bot.sh`, аналогично GUI.

**Размер:** ~500 строк, плюс тесты для очереди и команд.

**Зависимости:** `aiogram>=3` (одна внешняя зависимость). Нужно добавить `requirements.txt` (сейчас проект stdlib-only) и обновить README.

**Риск:** средний. Боль будет в:
- стабильно держать соединение через VPN (Telegram режется в РФ — нужен MTProto-прокси или работа через VPN);
- обработка крупных EPUB (>50 МБ) — Telegram режет, нужно слать через `sendDocument` с лимитом 2 ГБ для премиум, иначе разбивать.
